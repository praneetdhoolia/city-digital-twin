## What is built

- **THE DEPENDENCIES ARE PINNED, AND A DEPENDENCY CHANGE IS NOW A MODEL CHANGE** (§9.158). `requirements.txt` pins 11 directly-imported packages and 15 transitive ones, all at `==`, and `tests/check_requirements.py` **parses the repository's own imports** rather than trusting a hand-kept list; it is a CI job. No hashes: `--require-hashes` needs wheel downloads and PyPI is outside this repository's declared network sandbox, and the file says so rather than leaving the gap unstated. Until this the toolchain was pinned by sha256 while the Python that builds every artefact was whatever `pip` last resolved.
- **Build wall time is recorded for the first time, and it is OUTSIDE the hashed set** (§9.158). `src/build/build_timing.py` is called by 30 builders and lands in `cities/<city>/data/_build_timing.json`, gitignored and outside the manifest — **proved: 0 of 512 sha256 values moved**. A wall time inside a hashed artefact would churn every hash on every rebuild, which §9.155 already refused for a different reason.
- **The results store refuses to delete a run nobody can reconstruct** (§9.158, §9.137). `results_store.trim` would have deleted a run carrying no `_run.json` AND no findings in `processed/`; it now refuses. The two arms that guard caught were exactly that shape, and §9.159 closed them out properly rather than around it.
- **`run.py --stop` reaches the metrics extraction** (§9.158): an operator stop closed the run out but did not extract, so a stopped arm's findings depended on a later harness start noticing it.

- **A run that ends at a DEFINED BOUNDARY closes itself out** (§9.143): it reached its declared last iteration, the gate watcher stopped it under the GOAL.md loop, or the operator stopped it through `--stop`. Each writes `_run.json`, `_summary.json`, `SUMMARY.md` and extracts its findings. **A run that CRASHED still writes none** - it has no boundary and no defensible reading. The record's required `completion` field says which boundary, beside `reached_iteration` and the quoted `stop_cause`; **that field, not the file's presence, is the result gate**, and only `ran_to_last_iteration` satisfies resume matching or anchors a calibrated base. `reached_iteration` is the last iteration that ENDED, read from the log's own markers - never the progress digest's in-flight figure, which cost the F24 arm its gate reading. A record written before the field existed carries no `completion` and reads as `ran_to_last_iteration`; it is not required, because a frozen record is never rewritten to satisfy a newer schema (§9.143).
- **Three operations the session used to do by hand are scripts** (§9.155): `python src/run/session_gate.py --fix` regenerates every stale GENERATED artefact in dependency order (run index → config reference → schema → fit figures → board) and re-checks — it never edits prose, because a number in a living document is a claim a person wrote; `python src/analyse/compare_runs.py <a> <b>` reads two runs' own `stopwatch.csv` and REFUSES a comparison across a family (§3.5), a fraction or a profiled/unprofiled pair unless `--anyway` stamps the reason into the output, and flags a phase that fires in only some iterations rather than reporting its median as typical; `python src/run/verify_launch.py` executes the #70 sentence `run.py --detach` used to print for a person to act on.
- **`arm_cost.py` prices the iteration an arm REPEATS, and says what it cannot see** (§9.155, §9.156). It excludes profiled runs (the recorder is ~8 % of their clock) and names the newer runs it threw away rather than excluding them silently, which is how it once quoted **26.3 h** off a pre-repair arm. It then reads the priced run's own `output/stopwatch.csv` instead of its record median, because that median is a median over EVERY iteration and on a short probe most of those are iterations an arm pays once: iteration 0 warms the JIT, `dump all plans` fires at iterations 0 and 1 only, and the last iteration writes the final output. On `20260908T014214_4it_25pct` that is three of five, and the median read **282.6 s** against a recurring **216.0 s** (iterations 2 and 3) — a 31 % overstatement, trap 4 of the brief, which §9.155 taught `compare_runs.py` to flag and left in the pricer where it sets what an operator approves. It now quotes the recurring cost, carries the one-offs once each (326 s, 282 s, 350 s), and **warns when the priced run never reached a milestone iteration and so cannot have priced one**, naming the newest long arm as the top of the band. `tests/unit/test_plain_iteration_pace.py` pins it.
- **An unprofiled pricing probe is an overlay, not a thing a session improvises** (§9.156): `f30_plain_probe_25pct` is the profiling probe with the recorder and the GC log off and nothing else changed, so its clock is the arm's own. It opens no family.
- **The results store's trim window is bounded** (§9.155, #132). `RUN.storage.extract_grace_s` = 3600: past it a run whose `_metrics.json` never arrived is closed out, not protected forever. `RUN.storage.raw_cap_gb` is **gibibytes** despite its name — the code multiplies by 2^30 and the units field now says so.
- **One front door.** `run.py` resolves a scenario × day-type input set through `src/city.py`, applies a `--run-config` overlay from `cities/newcastle/overlays/runs/` and any `--set` overrides, and hands off to `src/run/run_matsim.py`, which emits the MATSim config, launches the pinned JVM and writes the run's records. `--iterations` has no default: a run states the horizon it used (§9.43).
- **Runs are named by the runner**, never by hand: `<launch yyyymmddThhmmss>_<iterations>it_<pct>pct`; the `--tag` flag is gone (§9.65). The stamp is a label, not identity.
- **Resume identity.** `find_completed` in `src/run/run_matsim.py` matches scenario, day, fraction, iterations, seed, `--set` overrides, the warm-start key, `rc == 0`, `controler_sha256` (the compiled Java), `values_sha256` (every resolved registry value in the run's `_config.json`, §9.104) and `inputs_sha256` (the day's population file, §9.127). A record lacking either hash never matches; `--force` re-runs. A run's identity is its inputs, not its parameters.
- **Three records per run.** `_meta.json` is the status card written at launch and at every transition — `running` / `completed` / `failed` / `aborted`, the identifying parameters, `pid`, `wall_s`, `rc`, `cause` — schema-checked against `config/schema/outputs/meta.schema.json` (§9.66). `_progress.json` is the machine-readable digest refreshed every `RUN.monitor.progress_interval_s` = 30 s: iteration, ETA, last mode shares, pace against `RUN.monitor.pace_band_s` = [217, 253] and the solo iterations `RUN.monitor.solo_check_iterations` = [2, 5] (§9.72, §9.76, #76). `_run.json` is written whenever a run ends at a DEFINED BOUNDARY — it reached its declared last iteration, the gate watcher stopped it under the goal's loop, or the operator stopped it through `--stop` — and its required `completion` field says which, beside `reached_iteration` and the quoted `stop_cause`. **The result gate is now that field, not the file's presence**: only `ran_to_last_iteration` is a result, satisfies resume or anchors a calibrated base, while a stopped arm's record is a citable reading at its `reached_iteration` and nowhere past it (§9.66). A run that CRASHED still gets no record at all — it has no boundary and no defensible reading — and states its cause on `_meta.json`. Records written before the field existed were only ever written on rc=0, so a missing value reads as `ran_to_last_iteration`. The card is written AFTER the inputs are validated, the config emitted and the run stack checked; a refused launch writes a `failed` card quoting the refusal and retires the directory under `aborted_` (§9.141, #127 closed; `tests/check_launch_refusal.py`). The card also carries `jvm_pid`, which `--stop` kills beside the harness pid (§9.141, #128).
- **The results store (§9.137).** `src/run/results_store.py` owns the layout: `results/raw/<run>` is the bulk cache under `RUN.storage.raw_cap_gb` = 500, trimmed oldest-first at every harness start and run end (live runs never; deletions logged to `results/processed/_trim_log.json`); `results/processed/<run>` holds the findings forever — every record file mirrored at each status transition plus `modes_trend.txt` / `modes_final.json` extracted at run end. **Nobody renames, deletes or edits anything under `results/` by hand**; eleven consumer modules resolve runs through the store. Trim keeps a completed run whose `_metrics.json` is not yet extracted and runs on a daemon thread after the launch, never in its path (§9.141, #132 closed); a processed twin left under a run's pre-abort name is reconciled at every harness start, and a hand-named run (`phys1000a_25pct`) resolves through its own record (§9.141, #137).
- **The runner gates its own run (§9.137).** A watcher reads all twelve modes every `RUN.gate.interval_iterations` = 100 iterations and, when any mode is at or past `CAL.gate.stop_deviation_pct`, kills the JVM itself and records the gate table as the abort cause (`_gate_stop.json`). The trend half of the loop stays a session judgement. A human-decided stop goes through `python run.py --stop <name> --cause "..."` — the one sanctioned manual path. **Its iteration source is `_progress.json`, not a log tail** (§9.139): the original 64 KiB tail was measured blind at the 25% log rate (ENDS marker 611 MiB behind EOF) and idled through the F23 gate. **The watcher fired live for the first time on the F25 arm** (§9.143): it stopped `aborted_20260905T125612_300it_25pct` at iteration 100 with seven modes past the bar and wrote the gate table as the cause, and the arm closed itself out with a record. Its stop is keyed on the reporter's verdict file, never the printed `GATE:` line (§9.141, #112 closed); an unready milestone is retried every `RUN.gate.retry_interval_s` = 300 s, and the log is read incrementally by a reader the digest shares, so neither reads more than the log's growth per cycle (§9.141, #131).
- **`run.py --stop` and `--list` need no valid registry** (§9.141, #126 closed): the sampler and the summariser read the registry on first use, so the one sanctioned way to stop an arm survives a registry mid-edit.
- **Detached launch.** `run.py ... --detach` registers and starts a Windows Task Scheduler task `citysim_run_<stamp>` so the JVM outlives the launching context (#70, closed). A launch is verified only when `matsim.log` progresses past `PersonPrepareForSim` with the launcher gone (§9.72). Stopping is `run.py --stop`, never by hand (§9.137).
- **A dead run says why, automatically.** The gate watcher writes its own cause; `run.py --stop` records the caller's; a crash is reconciled at the next harness start (`running` + dead pid → `aborted`, §9.66, §9.137). `src/run/run_failure.py --check` gates that every terminal record carries a cause (reading only the log's last 64 MiB, §9.136), and `results/INDEX.md` prints every cause (`src/analyse/build_run_index.py`).
- **Warm restart.** `--warm-start <dead run dir>` resumes from a dead run's newest plans checkpoint and records `warm_started_from` in `_run.json`; it is crash recovery, not a bit-identical continuation, and whether a warm-completed arm counts as an arm is a project ruling, not the harness's (#75, §9.76).
- **Live view.** `RUN.monitor.enabled` = true serves an observer-only page on `RUN.monitor.port` = 8731, re-reading every `RUN.monitor.poll_s` = 3 s and calling a run stalled after `RUN.monitor.stall_s` = 300 s of log silence (§9.36).
- **The toolchain** is fetched by `src/setup/bootstrap_toolchain.py` and pinned by sha256 in `.tools/toolchain.json`: JDK 25.0.4+7, pt2matsim 26.6 (embedding MATSim 2027.0-2026w25, §9.73), Maven 3.9.9 and the 201-jar signals run stack at that same MATSim version (§9.76). Signal runs execute `citysim.CitysimSignalsControler` on the run stack; every other run uses the shaded jar; the two never share a classpath. `--verify` re-hashes both and **recompiles both class trees** — it is not the read-only word it looks like (§9.156). Every component now passes an EXPECTED digest to `download()`: `PT2MATSIM_SHA256` was added 8 Sep because pt2matsim alone passed `None`, so its recorded pin described what arrived rather than what was expected, and it is pinned to the jar every mapped schedule in this package was built with (§9.156).
