Verdict

A remarkably well-documented, honestly-reported research codebase whose model build is complete and whose verification layer has a hole shaped exactly like its next step. In 24 days one author has produced a working twelve-mode MATSim twin, a 462-field declared registry with a hard-coding ledger at zero, a hashed 509-row data package, a frozen 13,800-line decision record and a document system with three CI-enforced drift gates. The prose-in-code is exceptional: every constant carries the section that decided it and the measured failure that motivated it. Against that, the project has no unit tests at all, no pull-request review, a run harness that would kill a healthy arm at its first passing gate, two acquisition scripts that cannot regenerate the data they produced, a manifest that carries no licence on 471 of 509 rows against a stated ODbL boundary, and a registry in which 94 % of the declared sweeps have never been run. Fourteen defects are confirmed at HEAD. None is subtle once named; all survive because verification is by whole-package inspection rather than by tests of the functions that decide correctness.

Build layer 34 files · 15,452 lines · 347 functions

Shape. A strict chain of 25 documented stages from OSM and census to the 30 run-input sets, each writing a build report that check_package.py reads; five builders (SA1-to-LGA map, licence rates, mode targets, dwell offsets, OSM defaults) have no documented position in the README's order. Determinism is real: every draw is a seeded generator or a hash of id and seed, outputs are sorted before writing, gzip and zip headers are pinned.

What is wrong. Nine defects: scenario configs written with absolute checkout paths and not re-run since the path refactor; a zip that misaligns building ids after the first skipped polygon; a pedestrian-phase flag that is 1 in both branches; a dead S2a call whose arguments contradict the live one; censored patronage cells treated three ways in two files; a false claim about escort trips baked into a committed parameter file; the project's most guarded number (charging dwell 20 s) typed into a corridor builder; sweep bounds duplicated beside values in five places so a registry change is invisible; the day-type token typed in the fare pricer. A typed Newcastle bounding box in src/build/gtfs_tools.py:6 is the exact class of defect issue #32 was about, still in the framework.

Ratings. Correctness 3 (every stage emits a report and ~60 invariants are cross-checked; nine defects pass all of them). Maintainability 2 (17 functions over 150 lines, write_day 544; haversine pasted five times; import-time file reads in 30 of 34 modules). City-agnostic 3. Determinism 4 (wall-clock stamps in two committed records; in-place mutation of A1_road_edges.csv by two later stages). Docs in code 5.

Run harness 10 files + 61 overlays · 3,544 lines · 124 functions

Shape. Resolve (registry, scenario, day, run overlays, env, CLI, each checked against the sweep), assemble the config through the emitter, write the status card, launch the JVM with a progress daemon and a gate watcher, wait, then mark dead or write _run.json, summarise, mirror to processed/, trim the cache. Identity is the parameter set plus three hashes, so a rebuilt demand cannot resume an older probe. Every non-obvious rule cites the incident that produced it.

What is wrong. The gate watcher stops on the literal text GATE:, which the reporter also prints on a pass. --stop and --list import the registry and die while anyone is mid-edit of it (reproduced during review). The status card is written before input validation, so a missing file leaves a run marked running with the real error lost. java.exe and a Windows-only JDK URL make a Linux launch impossible while the front door calls the framework portable. The progress digest re-reads the whole log from byte 0 every 30 s (51 GiB at a 25 % gate) while claiming to scan incrementally. results/raw holds 671 GiB against a 500 GB cap, so the next launch trims about 170 GiB synchronously, running the reporter on each directory first.

Ratings. Correctness 2. Maintainability 3 (three copies of _pid_alive; two CLIs drifting apart). Portability 1. Robustness 3. Docs in code 4 (stale claims that the iteration count is "unobtained").

Analysis and calibration 29 files · 10,129 lines · 272 functions

Shape. A finished run flows summarise → extract metrics (requires _run.json) → fit (calibration targets only, folded to the survey's categories through the city's reader adapter, every unscorable target listed with its reason, scored plus explained asserted equal to available) → report, figures, index. The per-iteration path rebuilds linked trips from experienced plans, scores twelve modes on two bases (trip share; boardings times 1/fraction) and prints the gate. The honesty safeguards hold: no path scores against an unscorable target and every reading is labelled not a result.

What is wrong. The reader stores a deviation for truck and freight rail and the board renders it: the committed board shows truck at −63.6 % beside "level only", the mistake §9.101 forbids. The replay-page builder references a module it never imports. A typed HTS vocabulary and vintage in measure_mode_constraints.py now disagree with the adapter fit.py uses. The smoke-run guard in the board generator swallows every exception and returns "not a probe". Vehicle mode is inferred from an id suffix in one script while its sibling documents that as the recorded trap.

Ratings. Correctness 3. Maintainability 2 (six functions over 150 lines; the schedule parsed in four places, the network in four, the results-store bootstrap pasted into eleven files). City-agnostic 3. Honesty safeguards 4. Docs in code 4 (49 % docstring coverage; report.py 1 of 13).

Ratings. Contract completeness 3. Check rigour 4. Registry provenance 3. Test coverage 2 (no unit tests; the only negative tests need the 2.3 GiB package). CI usefulness 3 (config reference drift and legacy drift never in CI; every job runs twice per PR; interpreter unpinned).
